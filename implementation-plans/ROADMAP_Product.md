Elapsed is a live, multi-tenant SLA / commitment-clock product. ## 3. Final decisions that still bind

Decisions are never reopened by implementation. If code conflicts with one, report the conflict first; after the owner's approval, change the decision here. IDs (D#) are cited by source comments and tests.

### 3.1 SLA engine semantics

- **D1** A new version of the *same* policy (override, re-import, policy-UI edit) does **not** change active commitments; only a switch to a *different* policy re-resolves. **D1b** A calendar change (reassignment or edit) applies to new commitments only.
- **D2** A breach is final; a target increase never un-breaches.
- **D3** After a reopen, the time spent solved does **not** count toward Resolution (the solve-to-reopen interval is excluded, like a customer-caused pause).
- **D4** Closing a case ends an open Next Reply cycle; a reopen followed by a customer reply starts a new one.
- **D5** A reply-less close is not "met" (it reports breached once past target and finalizes at the close). **D5b** On an agent-created ticket the First Response clock starts at the first customer message. *Documented semantic (owner, 2026-09-30):* when an agent replied before the customer's first message on such a ticket, that message opens both a First Response and a Next Reply obligation; Zendesk opens one. Not an engine defect; revisit if customers report duplicate reply alerts.
- **D6** Imported Zendesk policies match by Zendesk's own `position` (a positioned candidate outranks an unpositioned one; ties fall back to specificity). **D12** Imported policies are read-only (target overrides only) and match first; native policies follow by specificity. **D25** Imported policies do not count toward plan policy limits.
- **D7** On-hold never pauses Resolution (MVP). **D30** Imported Zendesk policies never pause Resolution on Pending (they mirror Zendesk); native policies keep the `pending_customer` pause.
- **Engine freeze.** A later phase that finds an engine problem goes back through a decision, then a test, then code; no quiet fixes inside UI work.

### 3.2 Product, accounts and notifications

- **D8** Deployment-level transactional email (`DEPLOYMENT_SMTP_*`, one shared config also used by ops alerts) for invites, resets and verification; `OrganizationEmailSettings` is per-organization, opt-in and never a dependency of account-recovery flows.
- **D9 / D17 / D18** Intercom and GitHub are Beta; **Linear is promoted out of Beta** (2026-10-05) and seeded Stable; Zendesk and Jira are Stable. Matrix roles: Zendesk + Jira = production baseline, Zendesk + Linear = matrix validation, Intercom + Jira/Linear = provider-boundary proof. Passing tests never promotes a provider or a pair; promotion is a separate explicit owner decision recorded here. GitHub is frozen: `code_host`, never an SLA source.
- **D10** The assignee is shown as a display name only, never used for analytics or scoring. **Organization timezone** is display-only (date display, pickers, dashboard grouping, report periods), never used in SLA math; a business calendar's own timezone drives SLA arithmetic.
- **D13** When a case's source integration is stale: at-risk alerts go out with a stale-data marker; **breach alerts are held** until the source is fresh again, then the case is re-evaluated and a confirmed breach is alerted exactly once. A held alert never consumes its `(commitmentId, threshold)` claim.
- **D26** A tracker admin who is not an Elapsed member connects through a signed, single-use, organization- and provider-scoped connect link (72 h, only a SHA-256 of the token stored).
- **Monthly report** (N5.6): idempotent per organization and month (`ReportDelivery`), operator kill switch `WorkerSettings.monthlyReportEnabled`. **Owner decision 2026-10-16 (OD-13): monthly reports stay enabled**; the setting stays `true` and no production setting or reporting code is changed. PDF reports, portals, AI summaries, financial figures and third-party analytics are out of scope.

### 3.3 Provider architecture

- **D16 (amended by D31)** One statically typed adapter contract with compile-time registries; no general-purpose connector framework, SDK, plugin system, dynamic loading or marketplace; no provider-specific SLA engine; provider knowledge only at the adapter boundary. The single exception is the declarative `custom` ticket-source engine (D31), which interprets validated configuration data and never executes customer code.
- **D19** A case's own ticket-source integration is its source of truth (`Case.sourceIntegrationId`, part of the case's unique key). Work trackers (Jira, Linear) and the code host are the engineering leg only, linked by `certain` links. **D23** Customer identity is normalized in `CustomerIdentity (provider, kind, externalId)`.
- **D22** Freshness is explicit: last successful sync per integration, recorded on evaluations and shown to customers and operators; circuit breaking only with evidence.
- **D24 Replay/diff gate** — see [Replay/diff gate](#replaydiff-gate-d24).
- **D15** Zendesk + Jira is the provider pair for the current customers and replay/test data; assignments are configuration, not architecture. Unverified for real customers (H-1); if a real tenant uses another pair, redo the affected replay classification.
- **D29** Zoho Desk is the third ticket source and the Egypt-market provider (N7), behind the provider contract, with a bounded backfill window (for example 90 days; measure API credit use in the spike), webhooks only where the edition supports them and polling/reconciliation as the correctness mechanism, OAuth, and protection against automation-generated replies being read as human first responses.
- **D31 Custom ticket provider.** One statically registered `custom` provider (`ticket_source`) interprets a versioned, closed-schema configuration. **Not negotiable:** customer code, scripts, expressions and plugins are never executed; the SLA engine, commitments and notifications packages stay provider-blind; source access is read-only; raw events stay append-only and replayable; Customer ≠ Requester; Conversation ≠ Activity Timeline; tenant isolation everywhere; any shared ingestion/commitment/notification change is subject to D24. **V1 scope:** one custom integration per organization; JSON over HTTPS only; `GET`, plus `POST` only on endpoints the owner designates as read-only search; page/offset/cursor/same-origin-next-URL/`Link` pagination; incremental sync by updated-since with look-back; API key in header, Bearer, Basic or custom header; **no OAuth; API keys in query parameters are prohibited**; required canonical fields external ID, created-at, current status; custom fields limited to tags and channel. **Deferred (each needs its own decision):** multiple instances, OAuth, webhooks, tracker/code-host roles, new canonical fields, arbitrary attributes in policy matching, templates/marketplace, configuration import/export, policy/calendar import, per-integration polling interval, undelete, raw-snapshot pruning. Rules, limits and reasons: [N9 design record](#n9-design-record).
- **D32** A successful sync that changed no data and recorded no failure creates no `IntegrationSyncRun`; failed, partial, aborted and ticket-failure runs are always stored. "Last checked" is `Integration.lastSuccessfulSyncAt`; "last data update" is `Integration.lastDataChangedAt`.
- **D33 Integration availability.** Each provider has an operator-controlled `enabled` switch independent of its stage (Stable, Beta, Coming Soon; "Disabled" is not a stage); Beta is open to all organizations or an explicit allowlist; no percentage rollout. One resolver answers "available to this organization?" on every path (connect, OAuth callback, connect links, config writes, backfill, webhooks, concierge exports, Custom REST routes, worker ingest, in-flight check). Refusals use `integration_disabled`, `integration_coming_soon`, `integration_beta_restricted` (403 / redirect); webhooks for an unavailable provider get **HTTP 200 and are ignored**. Disabling never deletes or rewrites integration rows, credentials, cursors, data or `Integration.status`; stored-data work continues and the source goes stale (D22, D13). Only `PLATFORM_ADMIN_EMAILS` operators; every change is one `AdminAuditLog` row with a required reason; writes are compare-and-set on a version. Slack is out of scope. Custom REST availability follows the same rules as every provider (the earlier N9.14-F1 rollout block was removed by the owner, 2026-10-12). Rules: [N10 design record](#n10-design-record).

- **D27 (amended 2026-10-16)** When a trial expires the account enters a restricted state that blocks new **configuration** only: new members, integrations and native policies (HTTP 402), with the in-app banner and an owner email. Cases that arrive from connected providers keep being ingested, evaluated and alerted ("new cases" is withdrawn). Monitoring is never gated by plan state.

### 3.5 Data retention

- **D34 (final, owner, 2026-10-10)** `RawEvent` rows and raw snapshots, for every provider (Custom REST latest and superseded snapshots included), have **no age-based expiry**. They are kept for the organization's lifetime and deleted **only when the organization is deleted** (procedure in `docs/data-retention-and-on-call.md`). Disconnecting an integration deletes none of it. Backups follow their own schedule; deleting an organization from the live database does not remove it from dumps already taken. **No retention job, scheduled prune or age limit is to be built.** N8-S6 may only partition or archive in a way that keeps raw events readable for replay and still removes them with the organization.

## 4. Product positioning and guardrails

- **Problem and wedge.** When a ticket is escalated to engineering the customer's clock keeps running while support's visibility stops, and the two systems produce different numbers. Elapsed keeps one honest clock across both and warns before the commitment breaks. Deterministic correlation through the official ticket-tracker link makes this feasible without fuzzy matching.
- **Ideal customer.** B2B SaaS, 80–400 employees, 6–25 support agents, 15–150 named accounts with contractual targets, a customer-facing helpdesk plus a separate engineering tracker and Slack; 40–400 escalations per month qualifies. Buyer: Head of Support; blocker: the VP Engineering who approves the tracker grant, so every first-run view must show engineering something it wants. Not the first vertical: MSPs, financial services/healthcare, agencies.
- **Positioning.** Lead with the escalation: *"Your SLA clock doesn't stop when the ticket leaves Zendesk."* Do not invent a category. The moat is neutrality between ticket source and tracker, not technology.
- **Neutral language, no exceptions** (the "no blame language" invariant): say "See where the time went", "Longest leg: engineering queue — 2h 17m", "Time by stage", "Engineering leg exceeded its 2h target", "contributing / elapsed / leg"; never "Prove who caused the breach", "Root cause: Engineering", "Delay attribution", "Blame / fault / responsible".
- **Evidence is a supporting feature**: a rendered timeline on the case page. No dispute packs, PDF exports, customer portals or e-signature workflows until a paying customer asks twice; never gate the timeline behind a tier.
- **Financial features stay out.** No service-credit, penalty or exposure calculation. The one allowed money-adjacent field is a manually entered account value or tier used only to prioritise. Revisit only after 10+ paying customers, a real contract corpus, an explicit request and a lawyer's review.
- **Onboarding principles.** No configuration before first value; ask for nothing the connected systems already hold; target under 15 minutes from sign-up to a findings screen; stream findings; deliver partial value from the ticket source alone; report link coverage honestly and never invent a link.
- **Unvalidated customer assumptions** (test with customers): 40+ escalations per month is the right threshold; the Head of Support controls the budget; customers have written contractual SLAs; the official ticket-tracker link is actually used rather than pasted URLs (the highest-leverage question).

## 5. Architecture invariants

1. **Store events, never computed time.** `RawEvent` is append-only; `NormalizedEvent` is derived and regenerable; elapsed time, deadlines and status are always derived; `Evaluation` rows are immutable and a breach *is* an Evaluation.
2. **The engine is pure** (`packages/core`): no I/O, deterministic ordering. Provider literals are forbidden in `@sla/core`, `@sla/commitments` and `@sla/notifications` (a boundary test enforces this); no provider package writes domain tables or depends on `@sla/commitments`.
3. **Versioned configuration.** Editing a policy or calendar appends a version. Re-resolution updates only active commitments, in place, audited in `CommitmentPolicyChange`, idempotent (D1, D1b, D2).
4. **Per-kind clock rules.** First Response and Next Reply never pause; Resolution pauses on policy pause states.
5. **Read-only integrations.** The only outbound writes are Slack and email alerts.
6. **Customer ≠ Requester; Conversation ≠ Activity Timeline.** The Conversation is rendered only through the source adapter's `renderConversation`; message-only.
7. **Multi-tenant by `organizationId`**, taken from the session and never from the client. Every new model needs a tenant-scope classification and isolation seeding.
8. **Operator is not an organization role.** Operators come only from `PLATFORM_ADMIN_EMAILS`; worker settings are operator-only and never exposed to tenants.
9. **Multi-worker scheduling.** Any number of workers may run against one database: per-organization work state with a lease (`FOR UPDATE SKIP LOCKED`), renewal, expiry recovery and a fencing token; active polling is start-to-start per organization; reconciliation is due at most 30 minutes after the previous pass; the per-organization advisory lock (`withOrganizationSlaLock`) remains a backstop for the projection phase. Per-organization pipeline serialization uses a Postgres advisory lock; no queue system.
10. **Provider credentials are encrypted at rest** (AES-GCM helpers; Custom REST uses strict per-value authenticated encryption, N9 §8.4). `priority_changed` is a display-only event the engine ignores.
11. **No AI, no blame language, no unnecessary architecture.** Deterministic behavior.
12. **Provider availability is persisted policy, not registration** (D33): registries stay static (D16).
13. **Commitment writes are conditional.** Status writes never overwrite `cancelled` and only apply while the policy version still matches. Re-resolution excludes `breached` commitments, while evaluation keeps evaluating an open breach so `breachedByMinutes` keeps growing; finished commitments never change.
14. **Alerts are claimed, then sent.** `claimNotifications` writes the claim rows inside the organization lock (DB only); delivery happens after the lock is released, in the worker and the webhook receivers; claims still `pending` after 15 minutes (a crash mid-send) are released so the alert is retried.

### Security and access rules that stay

- Tokens and OAuth client secrets are encrypted at rest; OAuth state is HMAC-signed and bound to organization, user and a cookie; webhooks verify a shared secret (and timestamp freshness) before any work.
- The organization always comes from the session or a signed token, never the request body; ids from a request are re-checked with an organization-scoped lookup before any write. Settings and integration mutations require the owner (`requireOwner`); a plain member is denied every owner route. Only `owner` and `member` roles exist.
- A role change or member removal bumps `sessionVersion` (the JWT is re-validated on every request); the only owner can be neither demoted nor removed. Password-reset, email-verification and invitation tokens are single-use, hashed, expiring and claimed atomically.
- Organization SMTP: a changed host or username requires the password to be re-entered (a blank password applies only while host and username are unchanged); non-public destinations (loopback, private, link-local, CGNAT, multicast, reserved, v4-mapped/NAT64/6to4/Teredo forms) are refused on save, test and every alert send; `SMTP_ALLOW_PRIVATE_HOSTS=1` is the documented local-development escape hatch only. Operator-configured SMTP is untouched.
- CSV exports neutralize formula-leading text cells (`=`, `+`, `-`, `@`, tab, CR) at the single writer `packages/core/src/csv.ts`.

## 6. Design rules still in force

### Replay/diff gate (D24)

Existing customer behavior must not silently change. Any change to `@sla/core`, `@sla/commitments`, a normalizer, correlation, or customer/case identity merges needs a recorded replay result **before it merges**.

```text
stored events (restored backup, read-only) → re-evaluate with CURRENT code → baseline capture
apply the change → re-evaluate the SAME stored events at the SAME asOf with NEW code → diff
target: zero unintended status / breachedAt differences
```

- **Compared per commitment:** `status`, `breachedAt` (the `effectiveDueAt` when breached), `effectiveDueAt`, `elapsedSeconds`, `remainingSeconds`, `clock.state`, `clock.pauseCause`, `warnThresholdCrossed`, `inputs.policyVersionId`, `inputs.calendarVersionId`, the evaluation `id`. **Per case:** the policy version `matchPolicyVersion` selects per kind, the Next Reply cycle plan, `deriveLegSpans` output, and the count of `certain` `CaseLink`s.
- **L1** (evaluation replay) is required for every change to `@sla/core`/`@sla/commitments`; **L2** (re-run normalization and correlation from `RawEvent` on the scratch database, then L1) is required for adapters, correlation, `Customer` or `Case` keys.
- **Where:** only on a scratch database restored from a backup (`scripts/restore-drill.sh` creates `sla_restore_drill`; `pnpm --filter @sla/worker replay:l2` refuses any other database). L1 opens a `READ ONLY` transaction. Never against the live database. Same `--as-of` for baseline and after.
- **Classes:** **A, unintended** — fix the change; it cannot merge. **B, intentional** — record decision ID, commitment/tenant counts, before → after, customer-facing effect and owner approval before merging; finalized commitments may be corrected but raise no new alert (`canRaiseAlert`). **C, pre-existing drift** — report the count and open a correctness task; it does not block.
- **Customer data rule:** capture files stay in the scratch directory, never in git; only aggregate counts and classifications are recorded.
- **Commands:** `pnpm --filter @sla/commitments replay:capture -- --as-of <ISO> --out <file.jsonl>` and `replay:compare -- <baseline.jsonl> <after.jsonl> --approved <approved.json>` (non-zero exit on any unlisted difference), with `DATABASE_URL` pointing at the scratch database.
- **Record:** approved class-B differences to date: none. Class C drift logged: 0 status / 10 `breachedAt` (2026-09-29 baseline, since closed as moot, see H-13 under [limitations](#8-accepted-limitations-and-unverified-claims)).
- **Incident rule:** if production evaluations diverge after a deploy, restore customer trust first (revert), run the comparison on a restored backup to find the class, then fix forward.

### N3 freshness rules and the N3.7 circuit-breaker design

- Freshness is metadata, never time math: `assessFreshness` (`packages/core/src/freshness.ts`) is pure; the default grace is 3 × the active-poll interval (`WorkerSettings.freshnessGraceFactor`, operator-only). It never changes `elapsedSeconds`, `status` or `breachedAt`. `Evaluation.sourceStaleSince` is the earliest `staleSince` of the case's source integration and any tracker with a `certain` link; a freshness change alone never creates an `Evaluation`. Evaluation always runs; monitoring is never hard-stopped for a tenant.
- `@sla/http-retry` sets a 30 s per-attempt timeout, up to 5 attempts and 60 s of total waiting, so the worst case for one request is ≈ 210 s; any budget wrapping provider calls must be sized against that.
- **If N3.7 is ever triggered:** after `consecutiveFailures ≥ 3` with `ProviderUnavailableError`, skip that integration's **ingest** until `Integration.nextAttemptAt` (additive, nullable); exponential backoff capped at the reconciliation interval; normalization and evaluation still run; reauth and permission-denied states are not outages; an operator switch in `WorkerSettings` disables it without a deploy. The trigger is in [§2](#2-remaining-work-and-gates). The ±10 % healthy-organization criterion (same-test control vs outage phase, with a 15 ms floor) and the 25 % bound (healthy organizations only, 7.5 s at a 30 s interval) are as validated by the W1/W2 tests on `testing`.

### N9 design record

> **The code is authoritative for behavior** (`packages/custom-ticket`, `packages/safe-http`, `apps/web/src/lib/custom-provider`, `apps/worker/src/sync-runs.ts`); this record keeps the rules and their reasons. Section numbers are cited by source comments and tests ("plan 09 §x" means the same-numbered section here). Original working tables and the configuration example (`packages/custom-ticket/src/schema.ts`) are in git history at `930c4ff` and earlier.

**§2.1 Rulings.** **Q1** provider-blind `Integration.slaSupport` (null for every existing provider); unsupported kinds are excluded in the shared commitments pipeline, not hidden in the UI. **Q2** the failed-record guard has a minimum count. **Q4** 120 s ingest wall-clock budget. **Q5** turning the Beta flag off (§8.7). **Q7** comment visibility acknowledgement (§5.2). **Q8/Q16** secrets (§8.4). **Q9** deferred pre-merge verification policy (since decided, Decision 9). **Q10** the "60 minutes" → 30 minutes reconciliation correction on the public integration docs pages (merged). **Q11–Q15, R1–R6** are carried by §4.3, §5.5, §5.6, §6.4, §6.9–§6.12 and §8.4. Reaffirmed: raw-event pruning stays deferred (D34); no synthetic status history; no closure timestamp inferred from `updatedAt`; no deletion based on absence from a sync response. Shared-code changes keep focused regression and D24 replay: sync-run recording (all providers), the optional `partial` ingest outcome and its `cycle.ts` branch, the no-change skip (D32), commitment-kind exclusion and cancellation (first code that cancels `first_response`/`resolution`), redaction, the `ProviderWebAdapter` config hook, the alert caveat, and the `@sla/email` re-export; `@sla/core` is untouched.

**§4 Capabilities**
- **§4.1 Configuration:** a versioned JSON document (`schemaVersion: 1`) validated by a strict Zod schema (unknown keys rejected, sizes bounded); the same validator runs on draft save, activation and worker load; it never contains a secret.
- **§4.2 Endpoints:** `tickets` (required), `comments`, `ticketDetail` (the only way to establish deletion by verified 404), `statusHistory` (real transitions only). Methods: `GET`, or `POST` with `readOnlySearch: true` set only by the owner's explicit confirmation. Variables (`{{cursor}}`, `{{page}}`, `{{offset}}`, `{{limit}}`, `{{updatedSince}}`, `{{ticket.id}}`) substitute only into URL-encoded path segments, query values and JSON string values, never scheme, host or port.
- **§4.3 Pagination and incremental sync:** page, offset/limit, cursor, same-origin next URL, `Link` header (RFC 8288, same-origin), each with page/item caps and repeated-cursor detection; incremental by an updated-since parameter with a configurable look-back. **R6:** activation is blocked for a source with no usable incremental cursor that cannot finish its initial full pass inside one run's limits (checked empirically, refused with the measured pages/tickets/requests/seconds). A source with a cursor may take many runs to import history and is shown as an import in progress, not a fault.
- **§4.4 Authentication:** API key in a header, Bearer, Basic, custom header; no OAuth; secrets write-only. 401 → `reauth_required`; 403 → `permission_denied`.
- **§4.5 Field mapping:** a constrained JSONPath subset (no filters, recursion, expressions or functions; `__proto__`, `constructor`, `prototype` rejected) and a fixed transform set (`packages/custom-ticket/src/schema.ts`). Required: external ID, created-at (→ `Case.openedAt`, set once), current status (explicit value map; drives `closedAt`). A closure timestamp is required to enable Resolution tracking; comments are required for Full SLA. No canonical home, deliberately: description, requester id/email, assignee id (D10), the source's updated-at.
- **§4.6 Status, priority, dates:** every external status maps to one of the eight `NormalizedState` values; an unknown value fails the record (`unknown_status`) unless the owner configures a fallback to `open`. An unmapped priority becomes `null` (`unknown_priority`), never a pass-through string. Dates: ISO 8601 with offset, or epoch; a date with no timezone requires an explicitly configured IANA timezone (UTC and the organization timezone are never assumed); nonexistent or ambiguous local times are rejected.

**§5 SLA modes and event history**
- **§5.1** `first_response` needs a ticket-source `case_created` with a correct actor and completion by `agent_replied` else `case_closed` (D5, D5b); `resolution` needs `case_closed` and `state_changed` for reopens (pauses on `resolved`, D3; native policies also on `pending_customer`, D30); `next_reply` needs `customer_replied` and `agent_replied`. Custom sources use **native** policies only.
- **§5.2 Modes:** **Full SLA** (tickets plus reply data with reliable author roles; the creation actor must be derivable) and **Resolution-only** (first response and next reply shown as unsupported). A terminal status without a reliable source-supplied closure timestamp blocks Resolution tracking (U7). **Q7:** with no reliable public/private field, Full SLA needs the owner's explicit acknowledgement that all returned comments are customer-visible, recorded inside the immutable configuration version (`commentVisibilityAcknowledged`, who, when), never defaulted, re-confirmed when the comments endpoint or mapping changes. The validator labels each metric `supported`, `supported with limitations` or `unsupported`.
- **§5.3 History is optional and never invented:** Elapsed never synthesizes `state_changed` or `case_closed` from polling observations. Current-status-only limitations: no customer-wait pause (Resolution can read longer), reopen detection limited to the net current state, sparse timeline, Resolution alerts on incomplete data (caveat shown).
- **§5.4 Enforcement:** `Integration.slaSupport` (e.g. `{ "unsupportedKinds": [...], "limitations": ["no_status_history"] }`) is written at activation and read by `runCommitmentPipeline`, `runNextReplyCyclePipeline` and `runCommitmentReResolutionPipeline`; `null` leaves existing providers unchanged. Notices on the integration page and case detail; at-risk and breach alerts for affected Resolution calculations carry a caveat line (`alertCaveatFor`).
- **§5.5 Commitments that become unsupported (Q14):** activating a version (including a rollback) whose `unsupportedKinds` includes a kind the integration already has commitments for requires a dry-run and explicit confirmation. Never delete a commitment, evaluation or notification; cancel only unfinalized commitments of the newly unsupported kind; finalized history untouched; idempotent. Confirmation is owner-only, bound to one integration, one target version and a hash of the exact commitment id set (a changed set voids it); cancellation and activation commit together with a `CustomActivationAudit` record.
- **§5.6 Rollback and cancelled commitments (R5):** `runCommitmentPipeline` never recreates or restores a cancelled `first_response`/`resolution`; `planCycleCommitments` **silently restores** a cancelled `next_reply` whose cycle is derived again, with its old clock. Policy: a rollback never reactivates a cancelled commitment; for `next_reply`, activation of a version that re-supports it is blocked while Q14-cancelled commitments exist (U3 option (a)); restoring cancelled commitments needs a new, separately reviewed reconciliation path (not part of N9) that decides whether a restored commitment resumes its old clock (a breach is final, D2) or starts a new one.

**§6 Synchronization, deletion and auditability**
- **§6.1 Flow:** initial import last 90 days by default (up to 365), resumable (cursor persisted after every completed page; `cursor.backfillCompletedAt` set only when the whole window is read). Each worker tick runs `ingest` outside the organization lock (raw events and cursor only), then `syncIntegration` normalizes and projects inside it. The incremental-poll / full-sweep normalization design remains a proposal, so `incrementalNormalization` stays `false` unless §6.10's correctness and performance evidence is produced.
- **§6.2 Limits:** per-attempt timeout 30 s (bounded by remaining budget); run budget 120 s; 50 pages and 5,000 tickets per run; 5 MB per response and 50 MB per run; 5 requests/s; JSON depth 20; stored payload 64 KB (larger fails its record `payload_too_large`, never truncated); live-case ceiling provisional and configurable (Beta 1,000).
- **§6.3 Budget (Q4, Q12):** one 120 s budget per ingest run on a monotonic clock covering every attempt, back-off, rate-limit wait and child request. Every request is bounded by the remaining budget; no attempt begins with under 1 s left. On expiry the in-flight request is aborted, its response discarded, nothing from an incomplete page is written, the cursor stays at the last completed page, and the run ends `partial` (`budget_exhausted`).
- **§6.4 Guards** (all inside `normalize()` before a batch is returned, so an abort writes nothing). Definitions at the start of the pass under the organization lock: **L** live cases of the integration; **B** distinct tickets in the pass; **F** failing members of B; **D** distinct live external ids in the deletion set; **R** live cases whose derived lifecycle state (open/closed) differs from stored; **N** distinct pass tickets that are not live cases.

  | Guard | Aborts when | Reason code |
  | --- | --- | --- |
  | Mass deletion | `D > max(3, 0.05 × L)` (no rounding) | `mass_deletion` |
  | Failed records (Q2) | `F ≥ 3` and `F > 0.25 × B` | `mass_record_failure` |
  | Mass lifecycle change (Q3, Q11) | `R ≥ 10` and `R > 0.25 × L` | `mass_lifecycle_change` |
  | Live-case ceiling (Q13) | `L + N > C` | `live_case_ceiling` |

  When the failed-record guard does not fire, failed records are excluded and reported individually, the rest projects, and the failed tickets' stored state is unchanged. An abort records reason, counts and up to 20 record ids on the sync run and `Integration.lastSyncError`, leaves cases/events/evaluations/watermark untouched, and **repeats on every pass until the cause is resolved**. `C` is `CUSTOM_PROVIDER_LIVE_CASE_CEILING` (integer 1–100,000, default 1,000), read by the worker once per pass per integration; a ceiling of 1,000 allows exactly 1,000 live cases. Boundary rows that must stay tested: failed records (B=3,F=3 abort; B=12,F=3 no; B=12,F=4 abort; B=100,F=25 no; B=100,F=26 abort); lifecycle (L=8,R=8 no; L=30,R=9 no; L=39,R=10 abort; L=40,R=10 no; L=40,R=11 abort; L=100,R=25 no; L=100,R=26 abort); deletion with L=101 the threshold is 5.05.
- **§6.5 Deletion:** a ticket is never deleted because it is absent from a list. Authoritative only on a reliable source signal (a status value or boolean the owner maps as "deleted") or a verified re-fetch (`ticketDetail` 404); either writes a `ticket_deleted:{id}:{hash}` raw event. The projector never clears `deletedAt`. A status/flag signal clears itself when the ticket is restored at the source; a verified-404 marker is permanent in V1.
- **§6.6 Idempotency:** raw events unique on `(integrationId, providerEventId)` (snapshots add a content hash); cases on `(organizationId, sourceIntegrationId, externalId)`; events reconciled by `diffNormalizedEvents`.
- **§6.7 Sync runs (D32):** one `IntegrationSyncRun` per attempt (outcome `ok|partial|failed|aborted`, a reason code for every non-`ok` outcome, counts, up to 50 `{recordId, code}` failures with no payload text), retained 30 days, recorded for all providers. A successful run that changed no data and recorded no failure is not stored; a data change is decided by a read-only before/after comparison in the shared projector.
- **§6.8 Configuration versions:** immutable once created; activation sets `Integration.activeConfigVersion` by compare-and-set; rollback re-activates an earlier version. Validation before activation: schema, connectivity, mapping against a live sample, the §5 mode checks. Mapping changes are forward-only by default; a change that could alter derived events or commitments requires the dry-run diff (`deriveBatch` over stored snapshots compared with `diffNormalizedEvents`, without writing); a configuration needing a field the stored projection lacks needs a re-import and shows its cost.
- **§6.9 Capacity (Q13, R4):** re-deriving the whole stored set on every pass is not an acceptable standing design, and 20,000 is not supported by any measurement. Until a ceiling is validated it is provisional, configurable and fails safely; never truncate, rewrite partially or skip the oldest tickets.
- **§6.10 Benchmark gate and result:** synthetic custom-shaped data through the real `deriveBatch`, guards and projector, tiers 1,000–20,000 live cases, full and incremental passes, a second organization and waiting webhooks concurrently, at least five runs per cell. Pass criteria: organization sweep p95 ≤ **30 s** and organization-lock hold p95 ≤ **10 s** (database-side only), memory inside the worker limit, query count and lock time no worse than linear. **Result (2026-10-10, OD-08):** harness `apps/worker/scripts/bench/custom-rest/` on a pinned 2-CPU host: 1,000 passes both limits; 1,500 passes and 2,000 fails; 5,000 fails lock hold (≈ 20.5 s); 10,000 and 20,000 fail both; cost is linear at ≈ 3.9–4.9 ms per case, dominated by the shared projector's per-case writes. Accepted only as a provisional Beta safeguard (C = 1,000); raw reports are in `docs/validation/evidence/d-01-benchmark/`. **Follow-ups:** a real-host benchmark (production host class and settings recorded, the production worker running concurrently, the same two limits at the proposed tier, second-organization and waiting-webhook cells included) is required before the ceiling is raised, after which the owner raises it to the largest passing tier; projector write batching is a separate item (byte-identical output on the D24 replay set, unchanged change counts and conditional writes, ≥ 3× projection-time reduction per case at 1,000 and 5,000 cases, lock-hold p95 at 5,000 cases ≤ 10 s). **Before the incremental design can be adopted:** equivalence with a full pass after randomized ingest/incremental sequences; watermark reset replays identically; crash safety; out-of-order commits and look-back overlaps not missed; deletion and lifecycle results equal to a full pass; forced full pass after configuration change, at activation and on operator request; D24 replay 0 differences for every existing provider.
- **§6.11 Override after a guard abort (Q15, R1, R2, U1, U2, U6):** no automatic bypass. Only the **mass lifecycle change** guard can be overridden; an override never bypasses the failed-record guard, the ceiling, the wall-clock budget, request limits, tenant isolation, security validation, the Beta flag or owner-only authorization, and **never forces a mass deletion**. Customer path (owner only; a `member` can never authorize): preview (guard, `R`, `L`, ratio, record ids, the open/closed flips), required reason, a confirmation bound to one integration, one guard and the preview hash (single use, expiring after 24 h), applied once on the next pass; a changed record set voids it. Support-assisted path: a separate permission (`GUARD_OVERRIDE_OPERATOR_EMAILS`; being a platform operator is not enough), the owner's recorded authorization for the same preview hash, a durable `GuardOverride` record (not pruned with sync history) and an `AdminAuditLog` row (`apply_guard_override`). Pilot: U2 option (b) (see §3.6).
- **§6.12 Partial runs and failures (Q12, R3, R6, U4, U5):** a run that ends **only because** its time or record budget is exhausted is `partial`, not successful and not a failure. Classification, in order: (1) 401/403, `credentials_unreadable`, not configured, or an unexpected exception → `failed` under the existing failure policy; (2) a provider or transport error that exhausted retries (5xx, network, TLS, `bad_response`, 429 that did not clear) → `failed` (the budget never turns a failing provider into `partial`); (3) a guard abort or a normalization/projection error → `aborted` (or `failed` for an error); (4) only the budget or a per-run cap → `partial` (writes `lastSyncAt` and duration; leaves `lastSuccessfulSyncAt`, `consecutiveFailures`, `failingSince`, `lastSyncError` untouched); (5) the final page completed and normalization succeeded → `ok`. `partial` reasons are `budget_exhausted` or `run_cap_reached`. Progress is kept only through the last fully completed page, committed with its raw events and the cursor in one transaction; `lastSuccessfulSyncAt` is set only by the run that completes the final page and its normalization. A partial run never releases a held breach alert and never clears the stale marker (D13(b)). A persisted run is superseded by a later clean check (`lastSuccessfulSyncAt > run.finishedAt`). Failed tickets are retried on every later pass. After three zero-progress runs in a row the next is `failed` (`no_progress`).
- **§6.13 Customer-facing sync states (R6, D32):** exactly one is shown, derived server-side (`lib/custom-provider/status.ts`): Importing history, Catching up, Up to date, **Needs attention** (real failure, guard abort, ceiling, `no_progress`, or `partial` for a source with no incremental cursor; never reported as a slow import), Paused / disabled. The stale-data marker (D13/D22) overlays any state. Copy never states a supported capacity.

**§7 Raw payloads, personal data and retention.** Stored: a whitelist projection of mapped fields and needed identifiers (the original key nesting is kept), 64 KB per payload; unmapped fields (emails, phone numbers, attachments, internal notes) are never stored; sample responses are never stored server-side; **no raw event is deleted by this feature** and superseded snapshots are not pruned (D34). Drafts and draft secrets expire after 14 days; sync runs after 30. **Disconnect** is the existing soft disconnect (credentials cleared, `status = disconnected`, all configuration versions and data kept and hidden by `packages/db/src/integration-visibility.ts`). **Reconnect:** `POST /api/integrations/custom/reconnect` with fresh credentials only, on `Integration.activeConfigVersion` (never the highest version or a draft), compare-and-set in one transaction with a `reconnect` audit row; activating a draft while a kept configuration is disconnected is refused (`reconnect_first`). **Delete configuration** (configuration only, no data purge): offered only while disconnected; deletes the draft and every configuration version and clears `activeConfigVersion`, `slaSupport` and credentials; everything else is kept; setting up again starts at version 1 on the same row and the first activation shows the dry-run diff against kept cases. Conversation rendering uses an optional config-loading hook (configured body and author paths at render time, so replay is preserved); message bodies are stored only if a body path is mapped.

**§8 Security**
- **§8.1 Destination rules** (every request, web and worker): WHATWG parse, `https:` only, port 443 only, no userinfo, length-limited; reject IP-literal hosts, `localhost`, single-label hosts and `.local`/`.internal`/`.localhost`; resolve and require **every** address to be public (`isPublicAddress`, `packages/email/src/destination.ts`, plus explicit denies for metadata names and `fd00:ec2::254`); a deployment-level local-development override (`CUSTOM_PROVIDER_ALLOW_PRIVATE_HOSTS`), never per organization; the ticket-URL template host must be HTTPS and public, matched by exact hostname equality, used only to recognize and display links.
- **§8.2 Pinning:** `undici@7.30.0` exact-pinned in `@sla/safe-http` with `Agent({ connect: { lookup } })` so resolution and validation happen inside the connect path (dual-stack returns the whole validated set and refuses if any record is denied); TLS hostname verification and SNI stay on; **one agent per ingest run**, closed at the end, never shared across runs or tenants; use `undici.request`, not `fetch` (no decompression, redirects not followed, streamed byte cap, `Accept-Encoding: identity`); proxy environment variables are ignored. Limitations: a customer API behind a corporate proxy is unreachable; no HTTP/2.
- **§8.3 Request rules:** only `GET`, or `POST` with a JSON body on an endpoint the owner confirmed as a read-only search; redirects disabled (a 3xx is an error); a next URL or `Link` target must be same-origin and pass §8.1; custom header names exclude `Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Cookie`, `X-Forwarded-*`, and CR/LF is rejected; credential-looking query keys (`key`, `token`, `secret`, `password`, `auth`, `signature`, `credential`) are rejected and a query value equal to a stored secret is rejected at request time.
- **§8.4 Secrets and redaction (Q8, Q16):** secrets are encrypted separately (`Integration.credentials.secrets`, encrypted draft until activation), never returned to the UI (only "set / not set"), never in configuration versions. `packages/db/src/custom-secrets.ts`: strict per-value AES-256-GCM, `enc:v1:` wire format, `INTEGRATION_TOKEN_ENCRYPTION_KEY` (distinct scrypt salt), bound by GCM additional authenticated data to `custom-secret:v1\0<organizationId>\0<integrationId>\0<field>` (a draft uses the literal integration id `draft`, re-encrypted at activation); it refuses to write or read an unprefixed value; every malformed form fails with the single generic `CustomCredentialsUnreadableError`, never returns plaintext, and has no plaintext fallback. Existing providers' encryption is untouched. **Rotation limitation:** changing the key makes every custom credential unreadable at once; owners re-enter them until N8-S7 exists. Decryption failure does not call the source and surfaces as a reconnect request. Credentials, authorization headers, sensitive URLs and payload data are removed from logs and worker error reports (`@sla/logger` scrubber), validation errors, sync history, `lastSyncError` and API/UI responses; custom client errors carry only `{status, endpointKey, classification}`.
- **§8.5 Outbound-request endpoints** (test, sample, preview, validate, dry-run): owner-only, same-origin check, rate-limited per organization, one request in flight per organization, and only safe classifications (`ok`, `blocked_destination`, `unreachable`, `timeout`, `tls_error`, `auth_failed`, `forbidden`, `rate_limited`, `bad_response`); a blocked destination never reveals which check failed or what the name resolved to.
- **§8.6 Tenant isolation:** every new model carries `organizationId`, is read through organization-scoped helpers, and has an entry in `apps/web/test/tenant-scope-classification.test.ts` and seeding in `tenant-isolation.test.ts`.
- **§8.7 Operator Beta flag (Q5; amended by D33):** the flag is the organization's entry on the Custom REST Beta allowlist, default off. Turning it off: no new outbound request or retry (checked before a run, before every attempt, at every page boundary); an in-flight request is aborted within about 5 s and its response discarded (`aborted`, `flag_disabled`); the same mutation sets `pollingPausedAt`; every manual outbound route refuses (`integration_beta_restricted`); data stays visible and DB-only stages continue, the integration going stale (D22); turning it back on does not resume a pause set separately.

**§9 Architecture**
- **§9.1 Packages:** `@sla/safe-http` (shared address classification, the pinned client, limits and budgets) and `@sla/custom-ticket` (schema, ingest engine, the pure `deriveBatch(config, rows)` used by preview, dry-run and the worker, adapter and web adapter); it imports only types and errors from `@sla/ingestion` and writes no domain table. Capabilities `webhooks`, `policyImport`, `calendarImport`, `priorityChanges`, `officialLinks` and `incrementalNormalization` are false; `replyEvents` is true only in Full SLA.
- **§9.2 Registration checklist for a new provider (also the N7 checklist).** Compile-forced: `IntegrationProvider` enum (migration with the `ADD VALUE` pattern), `apps/worker/src/providers.ts`, `apps/web/src/lib/providers.ts`, `INTEGRATION_PROVIDER_LABELS` in `apps/web/src/lib/types/integrations.ts`, `PROVIDER_ICONS`, `PRESENTATION` in `provider-presentation.tsx`, the catalog entry in `packages/db/src/integration-catalog.ts`. **Needed but not compile-forced (a miss is a silent bug):** the hand-written `IntegrationProvider` union, `INTEGRATION_PROVIDERS` and `IntegrationsPageData`; `getIntegrationsData`; `source-integration-specs.tsx` (real data; the existing cards show static placeholders, do not copy them); `lib/onboarding-data.ts`; `lib/security-summary.ts` (iterates `WEB_PROVIDERS`); `packages/db/src/plans.ts` integration lines; entitlements (counts by role; verify); the boundary test's `PROVIDER_PACKAGES`; admin and dashboard labels. **Deliberately not extended for custom:** `ConfigurableIntegrationProvider`/`IntegrationConfig`, `CONNECT_LINK_PROVIDERS` (trackers only), the five per-provider OAuth route sets, `REPORT_TICKET_URL_COLUMN`, `TICKET_SOURCE_KEY_PREFIXES`.
- **§9.3 Multi-instance later:** nothing new keys on `(organizationId, provider)`; a later expand migration adds `Integration.instanceKey TEXT NOT NULL DEFAULT ''` and replaces the unique key with `(organizationId, provider, instanceKey)` (26 non-test files mention `organizationId_provider`); known couplings to lift: `Case.system`/policy `sourceKey` is the constant `custom`, `CustomerIdentity.kind` needs an instance prefix, ticket-URL recognizers are keyed by provider name, labels come from `INTEGRATION_PROVIDER_LABELS`; the drafts table's per-organization unique is the only place V1 hard-wires "one".

**§15 Open items and risks.** Open owner items: the legal-review gate; U2 option (a) before GA; the real-host benchmark before raising the ceiling. **Risks kept:** capacity unproven beyond the Beta ceiling; a wrong creation actor freezes a wrong first-response clock; `deletedAt` is never cleared; raw snapshots accumulate for the organization's lifetime by design (D34), watched by the N8-S6 trigger; Resolution accuracy for current-status-only sources is limited and labelled; a guard abort repeats until resolved (a mass-deletion abort has no override); a key rotation makes every custom credential unreadable; per-ticket comment requests make large imports take hours; legal copy cannot be finalized without review.

### N10 design record

> Operator runbook: [`docs/integration-availability.md`](../docs/integration-availability.md). D33 holds the owner's rulings. Code: `packages/db/src/integration-availability.ts` and `integration-catalog.ts`, `apps/web/src/lib/integration-availability.ts` and `admin-integration-availability.ts`. Section numbers are cited by source comments.

- **§4.1 States.** `enabled` is independent of `releaseStage` (`stable`, `beta`, `coming_soon`); a Beta provider has `betaAccess` `all_organizations` or `allowlist`. `enabled = false` → nobody; `stable` → every organization; `beta` + `all_organizations` → every organization, Beta label; `beta` + `allowlist` → only listed organizations; `coming_soon` → nobody can connect or operate it. One resolver answers: `available`, or unavailable with `integration_disabled`, `integration_coming_soon` or `integration_beta_restricted`.
- **§4.2 Catalog versus policy.** `INTEGRATION_CATALOG satisfies Record<IntegrationProvider, …>` (display name, category, connection type, default availability) is static (D16); the policy is data (`IntegrationAvailability`, one row per provider with a `version` for compare-and-set; `IntegrationBetaAllowlist`, primary key `(provider, organizationId)`); a missing row falls back to the catalog default. Seed: Zendesk, Jira, Linear stable; Intercom and GitHub beta + `all_organizations`; `custom` beta + `allowlist`.
- **§5.1 Resolver.** `getIntegrationAvailabilityPolicy`, `listIntegrationAvailability`, `resolveIntegrationAvailability(db, organizationId, provider)`, `resolveOrganizationAvailability`; **no cache**: every check reads the database, so a change applies to the next check in every process.
- **§5.2 Web.** `requireIntegrationAvailable` returns 403 `{ error, code, provider }`; OAuth GET routes redirect via `availabilityRedirect` to `/settings/integrations?availability=<code>&provider=<provider>`. Gated after authentication and before any provider call or write: connect, callback (the code is not exchanged, no credentials stored, a connect link not consumed), connect-links create/start, config POST/DELETE (GET stays readable), backfill, Zendesk/Jira webhooks (**200** `{ status: "ignored", reason }` after the secret check, before parsing, nothing stored), concierge exports, and `custom/*` via `ownerGuard` (`status` and `disconnect` pass `requireAvailable: false`: a customer can always see and disconnect a paused source). `integration-availability-boundary.test.ts` fails if a route under `app/api/integrations/**`, `app/api/webhooks/**` or `app/api/concierge/**/export` neither calls the helper nor is on the exemption list (disconnect routes, Slack, connect-link revoke).
- **§5.3 Worker.** `processOrganization` reads `resolveOrganizationAvailability` once per organization run before ingest; an unavailable integration is skipped exactly like the N4.5 operator pause (no provider call, no sync attempt recorded, no failure, no `failingSince`; log `integration_ingest_unavailable`). Normalization, commitments, evaluation and alerts on stored data keep running and the source goes stale (D22; D13(b) holds breach alerts). `runCustomIngest` re-checks before the run and in its 5 s in-flight check. Built-in providers have no in-flight abort. An unreadable policy fails closed (no provider call, stored data still evaluated).
- **§5.4 Custom REST allowlist.** Removing an organization from the allowlist sets `pollingPausedAt` on its custom integration in the same transaction; re-adding never resumes a pause. An allowlist add is scoped to that organization, validated and audited (`addToBetaAllowlist`). The admin API applies the same rules to Custom REST as to every provider.
- **§5.5 Customer-facing.** An unavailable provider shows as Unavailable or Coming soon (with the operator's message) with no connect control; a Beta-restricted provider is hidden from organizations not on its allowlist; a connected integration whose provider becomes unavailable shows **"Paused by Elapsed"**, never "Disconnected" (`Integration.status` is never changed; the customer may still disconnect but not reconnect).
- **§5.6 Stage wording.** The persisted `releaseStage` is the only source of Beta/Stable/Coming-soon wording (`apps/web/src/lib/release-stage.ts`, `components/shared/release-stage.tsx`, `lib/release-stage-data.ts` for the public `/docs/integrations/*` pages and home list, rendered per request). No copy is edited on a promotion; a stage is not a connection status or sync health. Markdown guides carry no stage. Slack has no stage.
- **§6 Lifecycle.** Disabling leaves integration rows, credentials, cursors, webhook secrets, raw events, cases, events, commitments, evaluations and notifications unchanged; re-enabling repairs nothing: the next run ingests from the stored cursor (Zendesk's incremental export `start_time`, Jira's `updated >= updatedSince` JQL recover ignored webhooks), and an integration that was `disconnected`, `reauth_required` or operator-paused stays that way. Availability and disconnect (`Integration.status`) are different columns and never written by the same action.
- **§7 Admin console and API** (`requirePlatformOperator`). `/admin/integrations` shows per-provider stage, Beta access, allowlist size, connections and health, with an edit dialog that needs a reason and shows an impact preview before narrowing; `PATCH /api/admin/integrations/providers/[provider]` takes `{ expectedVersion, enabled?, releaseStage?, betaAccess?, statusMessage?, reason }` (400 invalid, 409 `stale_version`, a no-op writes nothing) via `updateMany({ where: { provider, version: expectedVersion } })` with `version` incremented; allowlist add/remove (duplicate → 409 `already_listed`). **Audit:** one `AdminAuditLog` row per write in the same transaction (`update_integration_availability` with `{ provider, before, after, reason }`, `add_integration_allowlist`, `remove_integration_allowlist`); never a credential or configuration payload.
- **§8 Security.** Only `PLATFORM_ADMIN_EMAILS` operators can read or change availability; owners and members get 403 from the API and `notFound()` from the page; no organization-level setting overrides a platform restriction; credentials are never selected; the customer-facing message is operator text rendered as text.
- **§11 Rollback.** After N10-F1 the `customProviderEnabled` column is gone, so pre-N10 code cannot run without restoring it (`ALTER TABLE "organizations" ADD COLUMN "customProviderEnabled" BOOLEAN NOT NULL DEFAULT false`, then re-set it from the Custom REST allowlist); the migration's `rollback.sql` re-adds it from the allowlist.
- **§12 Out of scope.** Percentage rollout, an "internal organizations" concept (use the allowlist), Slack, per-plan availability, database-backed admin roles, an in-flight abort for built-in providers, listing providers that have no adapter.
